# 为什么这个站点用原生实现，而不是 React

date: 2026-10-15
tags: 前端, 工程取舍, 性能

做个人展示网站时，我遇到一个很实际的问题：**该不该上框架？** 这篇记录我的判断过程，以及最后的取舍。

## 先看需求到底需要什么

把 PRD 拆开看，这个站点要做的事其实只有五件：

1. 展示静态内容（介绍、技能、项目）
2. 解析 Markdown 渲染博客
3. Canvas 画星空背景
4. 表单校验
5. 多端适配

这里面**没有任何一项需要框架**。没有复杂状态同步，没有跨组件通信，没有需要服务端渲染的 SEO 诉求。框架能带来的收益，在这个场景里几乎为零。

## 框架的成本在哪里

框架不是白拿的，代价至少有三块：

- **构建链**：装上 Vite + React + TypeScript，`node_modules` 轻松几百 MB，冷启动要等十几秒；
- **认知负担**：以后想改一行文案，得先回忆 `npm run dev` 怎么起、依赖装没装；
- **长期维护**：三年后回来看这个项目，依赖版本全过期，先花半天升级再说。

对个人站点这种**改一次放半年**的项目，第三点最致命。

## 决定性因素是环境

真正让我下决心的，是开发环境的实际情况：

```bash
$ which npm
npm not found

$ npm ping
# 网络不通
```

这台机器上只有独立的 `node.exe`，没有 npm，也没有任何包缓存，并且处于离线环境。

假设我坚持用 React 写完，结果是：

> 代码写完了，但 `npm install` 跑不起来，项目**根本打不开**。

一份跑不起来的漂亮代码，价值是零。所以选择很清楚了。

## 原生方案怎么保证不失控

放弃框架不代表放弃工程性。我做了三件事来兜住可维护性：

### 1. 设计令牌集中管理

所有颜色、圆角、间距、动效时长都定义在 `:root`：

```css
:root {
  --bg: #0B0F1A;
  --text: #E6EAF2;
  --accent: #5B8CFF;
  --radius-lg: 16px;
  --t: .3s cubic-bezier(.22, .61, .36, 1);
}
```

改主题只需改这一处，不需要全局搜索替换。

### 2. 数据与结构分离

技能、项目这类会变的内容，抽成 JS 数组再渲染：

```js
var PROJECTS = [
  { title: '图提取', tags: ['MV3'], demoUrl: '...' }
];
```

加一个项目 = 加一个对象，不碰 HTML。

### 3. 用平台能力替代库

| 常见库 | 原生替代 |
| --- | --- |
| 滚动动画库 | `IntersectionObserver` |
| 平滑滚动库 | CSS `scroll-behavior: smooth` |
| 状态管理 | 直接操作 DOM |

> 判断标准很简单：如果这个能力浏览器本来就支持，那引入库只是在为「不查文档」付费。

## 代价我也认

原生方案不是没有缺点，说清楚：

- 组件复用靠手动复制，没有 props 机制；
- 没有类型检查，重构时得靠自测清单兜底；
- 内容变多后，手写渲染代码会比 JSX 啰嗦。

对这个规模的站点，这些代价可以接受。**如果哪天要加用户系统、后台管理、实时协作，我会立刻换成框架** —— 技术选型应该跟着需求走，而不是反过来。

## 小结

- 先问需求需不需要，再问自己想不想用
- 环境约束是硬约束，跟它较劲没有意义
- 放弃框架不等于放弃工程性，令牌化 + 数据分离 + 平台能力就够撑住中型静态站点

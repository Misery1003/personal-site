# 把开发流程写成文档，AI 的产出才稳定

date: 2026-10-05
tags: AI 编程, 工作流, 文档

用 AI 写代码最大的问题不是「写不出来」，而是**写出来的东西每次都不一样**：这次用 React，下次用 Vue；这次目录叫 `components`，下次叫 `views`。项目稍微大一点就开始互相打架。

我现在的做法是：动手写代码之前，先产出三份文档。

## 三份文档分别解决什么

### PRD.md —— 解决「做什么」

写清楚目标用户、核心功能、优先级、验收标准，以及**明确不做什么**。

最后一条最容易被忽略，但最有价值。比如我写个人网站时明确列了：

> 明确**不做**的：用户注册登录、评论系统、服务端接口。

不写这句，AI 很可能「贴心地」帮你加上评论功能，然后你就得维护一个本来不需要的后端。

### TECH_DESIGN.md —— 解决「怎么做」

包含四块：技术栈选择、项目结构、数据模型、关键技术点。

其中**技术栈选择要写理由，不能只写结论**：

```markdown
| 层 | 选型 | 理由 |
| --- | --- | --- |
| 样式 | 原生 CSS + 设计令牌 | 无构建步骤，改主题只需改一处 |
```

有理由，AI 才不会在你换环境时还死守原方案。

### AGENTS.md —— 解决「按什么规矩做」

这是给 AI 的约束文件，写开发规范、代码风格、测试要求、以及**不要做什么**。

关键是「不要做什么」这一节要具体：

```markdown
- ❌ 不要为了「更现代」而引入框架或构建工具；
- ❌ 不要把样式写成内联 style="..."；
- ❌ 不要提交 node_modules/、构建产物、编辑器配置文件。
```

比起笼统的「请写出高质量代码」，这种可执行的禁令有效得多。

## 为什么有效

### 1. 把一次性对话变成可复用资产

对话会消失，文档会留下。下次新开一个会话，把三份文档丢进去，AI 立刻就能进入状态，不需要你从头解释一遍。

### 2. 把「约定」从脑子里挪到纸上

很多规范你自己心里清楚但没说出口。写文档的过程就是逼自己把隐式约定显式化的过程——**往往写到一半就发现自己原来的想法有矛盾**。

### 3. 让验收标准可执行

PRD 里我写的是这种能直接测的条目：

```markdown
- [ ] 375px 宽度下无横向滚动
- [ ] 移动端星空帧率 ≥ 50fps
- [ ] 控制台无报错
```

而不是「界面美观、体验流畅」这类没法验收的话。

## 实际怎么落地

我的流程是三步迭代，不追求一次到位：

1. **先跑通骨架**：让 AI 生成能运行的基础结构，丑一点没关系；
2. **逐个实现核心功能**：一次一个功能，做完就测，测完就提交 Git；
3. **最后打磨细节**：性能、动效、无障碍。

中间用 Git 兜底：**每个能跑通的功能提交一次**。这样即使后面 AI 改崩了，回退一步就能回到可用状态，不用在废墟上重新盖楼。

## 一个真实的反面案例

早期我做插件时直接在对话框里说「帮我做个提取图片的扩展」，结果：

- 权限申请了一大堆用不上的（包括 `<all_urls>`）
- 目录结构每次都不一样
- 改一个功能把另一个改坏（典型的「左右脑互搏」）

后来补上三份文档，同样一句话的需求，产出的代码结构稳定、权限最小化、注释也规范了。

## 小结

- 三份文档分别对应：做什么 / 怎么做 / 按什么规矩做
- PRD 一定要写「不做什么」，TECH_DESIGN 一定要写「为什么选它」
- 规范要写成可执行的禁令，不要写成口号
- 文档是资产，对话不是
